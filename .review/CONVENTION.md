# .review — shared convention

Canonical copy: `~/.claude/review-convention.md`. Synced into every repo with
a `.review/` directory by `~/bin/review-sync`. **Do not edit this file inside a
repo** — edit the canonical copy and re-run the sync, or the change is lost.

A repo may also keep its own `.review/README.md` for repo-specific notes. That
file wins where the two disagree, and should say so.

## The loop

1. A chat session writes the next task to `.review/next.md`.
2. `dispatch <project> "/review"` opens a Claude Code session and sends it.
3. Claude Code does the work, writes the full report to `.review/report.md`,
   and archives both to `.review/archive/`.
4. The chat session reads `.review/report.md` directly.

Presence of `next.md` means a task is waiting. `.review/running` is a
lockfile; `dispatch` refuses to start a second session on a repo that has one.

## Premise provenance — added 2026-09-04

Three consecutive tasks across three repos were written on premises that turned
out to be false. In every case the premise came from a previous report, and in
at least one case the original report had explicitly hedged it — *"that is a
code-reading finding, not a measured one"* — and the follow-up task promoted
the hedge to a stated fact.

Therefore:

* **Every task states where its premise came from**, as `file:line` for a
  source claim or as the measurement for an empirical one. "The report says"
  is not provenance; the report is not the code.
* **Hedges carry forward.** If the source was code-reading rather than
  measurement, the task says so in the same sentence. A task may not launder
  an observation into a fact by restating it without its qualifier.
* **Step one of any task is to verify the premise in live source**, and to
  report file and line for what it actually found. This step has paid for
  itself on its first use in each of the three repos.
* **If the premise is false, stop.** Report that, and do not build a fix for
  a defect that does not exist without asking. The finding is the deliverable.

This applies to tasks a Claude Code session writes for itself as much as to
tasks a chat session writes. Self-written follow-ups have been the larger
source of the problem, because a session trusts its own prior reasoning more
readily than someone else's.

## Deferred findings must be machine-readable — added 2026-09-04

Sessions find more than they fix, deliberately: diagnose-before-fix, one thing
per cycle, out-of-scope items left alone. That is right, and it has a failure
mode. Over weeks the findings scatter across report prose, `hot.md` lines and
decision-log entries, and nobody can answer "what did we find and never fix".

So every report ends with a `## Deferred` section, even when it is empty:

```
## Deferred

- [ ] FINDING: <one line, specific enough to act on> | where: <file:line> | class: actionable|human|elsewhere | severity: high|medium|low
- [ ] FINDING: ...
```

Or, when there are none:

```
## Deferred

none
```

### The class field, added 2026-09-05

A sample of 33 findings, each checked against live source rather than against
the report that recorded it, came out roughly half actionable, a fifth needing
Thomas's decision, an eighth already fixed and never ticked, and a fifth too
vague to act on. Nothing in the line distinguished them, so anything reading
the backlog had to re-derive all of that by hand.

* **`actionable`** — a session could pick this up and know what done means.
* **`human`** — Thomas's decision, a policy question, or a dashboard setting.
  Nothing automated may act on it.
* **`elsewhere`** — real, but the work belongs to a session in another repo.
  Name that repo in `where:`. Findings about `~/iris` recorded from another
  repo are the common case and must not be actioned from where they were
  written.

  The test is *which repo's session does this work*, not where the file sits
  on disk. Worked example, settled 2026-09-05: `~/.claude`, `~/.codex`,
  `~/bin` and `~/Developer/ECC` have no `.review/` of their own, and every
  task that has touched them ran from `~/dev/orchestra`, so orchestra owns
  them. A finding about one of those trees recorded from orchestra is
  `actionable`; recorded from any other repo it is `elsewhere`, and the path
  under the tree is enough to say whose it is. `classify.HOME_OF` in
  orchestra encodes the same ownership; do not re-derive it.

**There is no `vague` class, deliberately.** If you cannot state what done
looks like, it is not a finding yet — write it into the report's prose
instead. A fifth of the backlog was unactionable observations that had been
promoted to findings because the format made it easy.

### The rate matters more than the count

Measured 2026-09-05: reports generate about **seven findings each** and close
well under one. That ratio, not the total, is what makes a backlog
unmanageable, and it was true before any orchestrator existed to consume it.

So: **a finding must earn its line.** Before writing one, ask whether a
session could act on it and whether anyone would be worse off if it were left
out of the report entirely. If the honest answer to either is no, it belongs
in prose. Ticking one you have confirmed fixed is worth as much as recording a
new one — four of the 33 sampled were already fixed and nobody had ticked
them.

Rules:

* **One line per finding**, starting `- [ ] FINDING:`. `review-findings`
  harvests these across every repo, so the prefix is load-bearing.
* **`where:` names a file** — `path:line`, or a path when the line would be
  a guess. "capture path", "the SSE server", "dashboard" and a directory are
  not places anyone can open. `human` findings may name the setting or page
  the decision lives in instead; `elsewhere` names the repo. `review-verdict`
  prints `UNACTIONABLE` for an open `actionable` finding whose `where:` names
  no file and exits 1, the same as a contradiction. Added 2026-09-05, when it
  measured 12 such lines across 198 archived reports (182 open `actionable`
  findings at the time). Those are the owning sessions' to fix one at a
  time — nobody rewrites a `where:` by guessing which file was meant.
* Anything the task declared out of scope, anything found while working that
  was not fixed, and anything recommended but not implemented goes here.
* Mark it `- [x]` only when the fix has actually landed and its commit is
  named in a later report. Do not tick your own finding in the same run.
* Severity is about consequence if left alone, not effort.
* A finding that turned out to be **false** is still recorded, ticked, with
  `(refuted: <what the evidence showed>)`. Refuted findings are how the same
  wrong path stops being retried, and three tasks were built on false premises
  in a single day for want of this.

Run `review-findings` to see every open one across all repos. If it prints
something that has in fact been fixed, tick it in the archived report rather
than arguing with the tool.

## The verdict is a fixed header — added 2026-09-05

A report's verdict used to be prose. Across the 185 reports archived in
eleven repos by 2026-09-05, 116 had no verdict word in any fixed place
(three more had one only in running prose), and the 69 that did used nine
different prefixes: `RESULT PASS`, `RESULT: **PASS**`, `Result: PASS.`,
`**RESULT: PASS**` and so on. Nothing could read them, so the only way to
know whether a task succeeded was a human reading each report — the session
marking its own work, one level up. Measured with `review-verdict --survey`.

Every `report.md` therefore opens with this block, directly under the title
line, one field per line, in this order, no bold, nothing else on the
`RESULT:` line:

    RESULT: PASS | PARTIAL | FAIL
    GATE: green | red | unmeasurable | not-run
    SESSION: <the value of $CLAUDE_CODE_SESSION_ID>
    HUMAN: none | <what still needs Thomas — a confirmation or a decision>
    PREMISE: held | false: <one line on what was not true>

Why each field, from a report that needed it:

* `RESULT` — one word. PARTIAL means some of it was done, or it was done
  but not verified, or a judgement call is waiting on Thomas. That is the
  /review definition, and it has a consequence under `HUMAN`.
* `GATE` — what the session believes the gate did. This is the one field
  that is cross-checked: `~/.claude/state/gate-log.tsv` holds what the gate
  actually did. `atrium-surface/2026-09-05T1312` said `RESULT PASS` while the
  log recorded `unmeasurable` in the same minutes; whether the session knew
  the gate had measured nothing is not recoverable from the report.
* `SESSION` — the join key, and since 2026-09-17 the one field that is not
  optional. `gate.py` writes the session id into the log (field 6, since
  2026-09-05). Without it the join is by repo path and time; the Stop hook's
  row follows the archive by a median of 1 minute (62 of 65 within 5), usable
  but not exact. `atrium-surface/2026-09-05T1203` archived with no verdict and
  the gate blocked at 12:04 and 12:07 — whether that was the same session is a
  guess without the id. 201 of the 428 reports archived by 2026-09-17 have no
  `SESSION:` and are unjoinable forever, which cost one analysis half its data.
  `review-verdict` now prints `NOSESSION` and exits 1 for a report written on
  or after 2026-09-06 without it. Reports before that are grandfathered: a
  census on 2026-09-17 found the last one missing the field was written
  2026-09-05, so the rule refuses nothing in today's archive and only stops the
  next one being written.
* `HUMAN` — what is still Thomas's. `iris/2026-09-05T1900` said
  `RESULT: PASS (by-ear confirmation is MANUAL, see §7)`;
  `orchestra/2026-09-05T0042` said `PARTIAL — one judgement call is waiting
  on Thomas`. Same situation, two verdicts. Five archived PASS reports carry
  a human step in their opening lines. Under the /review definition a PASS
  with `HUMAN` other than `none` is a contradiction, and `review-verdict`
  says so.
* `PREMISE` — whether the task's stated premise held. The Premise provenance
  section already requires checking it; this records the answer where a tool
  can read it. Nine archived reports found their premise false or wrong
  (`orchestra/2026-09-05T1256`: the token was already dead;
  `iris/2026-09-03T1925`: "the premise is wrong"). A PASS on a false premise
  means the work done was not the work asked for; a routing experiment that
  counts it as a success is measuring nothing.

What is derived and what is claimed. `SESSION` is copied from the
environment. `GATE` is a claim, but the log holds the truth, so a wrong
claim is caught. `RESULT`, `HUMAN` and `PREMISE` are the session's own
statements and stay that way: "the acceptance criteria held" is a judgement
and no script derives it. The value is that the claim now has a fixed shape
and two automatic contradictions — `RESULT: PASS` with a red gate in the
log, and `RESULT: PASS` with `HUMAN` not `none`. There is no score.

`~/bin/review-verdict` reads the block, joins it to the gate log, prints
every contradiction and exits 1 if there is one. Since 2026-09-05 it also
prints `UNACTIONABLE` for a Deferred line that breaks the `where:` rule
above, with the same exit. `review-status` shows the
last report's verdict per repo, with `!RED` or `!HUMAN` appended when it
contradicts and `*` when the shape is pre-convention. Reports archived
before 2026-09-05 do not carry the block and are not retrofitted;
`review-verdict --survey` counts them.

## Findings cap — added 2026-09-06

Firmer wording did not work. Measured 2026-09-05: findings per report went
from 6.96 before "the rate matters more than the count" landed to 7.53 after
it, no downward trend by hour, and the one check that existed (`UNACTIONABLE`)
does not touch the count. Full measurement in
`orchestra/.review/archive/2026-09-05T2325-measure-whether-they-wrote-fewer-findings.report.md`.
Advisory prose that nothing checks does not change behaviour; a mechanism
does.

**At most three open findings per report.** `review-verdict` counts the
`- [ ] FINDING:` lines in `## Deferred` — ticked lines (`- [x]`) never
count, so closing findings is always safe and never discouraged — and exits
1 when the open count exceeds the cap, the same way `RESULT: PASS` with a
red gate does. The message names the count and the cap, and says where the
rest goes.

**Open, not open-plus-closed, is the counted set**, deliberately: a report
that ticks six and opens two must not fail, because that report is draining
the backlog, not growing it, and a cap that punished ticking would recreate
the asymmetric incentive this rule exists to remove.

**A per-task override.** A line `Findings cap: N` in the task — `next.md`
while the cycle is live, the archived `*.task.md` afterward — raises the cap
for that one report. Genuine audits produce more than three real findings
(the Finance-Tracker account surface found 19), and the cap must not punish
them for it.

**Everything beyond the cap goes in the report's prose**, where the
reviewing chat reads it anyway. A finding dropped for the cap is not a
finding left unrecorded — it is a finding recorded somewhere `review-findings`
does not harvest. Say that in the report, not just in this convention.

**No report archived before 2026-09-06T09:00 is retroactively failed.** The
check only applies to reports timestamped at or after that moment, the same
grandfathering the verdict header got in 2026-09-05: an old report simply
predates the rule it did not have.

**Re-measurement.** The number that shows this worked is findings-per-report
over the days after the cap goes live, on the same "every fifth report,
checked against live source" method as the 2026-09-05 sample — not the raw
count, since a session could satisfy a count cap by writing three findings
and dropping four real ones into prose where nothing drains them either.
Look again once at least 15 reports have been archived under the cap (the
same sample size the before/after comparison used), not before, and say
what the drain-to-source ratio is, not just whether reports stayed under
three.

## A task declares its shape — added 2026-09-17

A task file may carry one line:

    SHAPE: diagnosis | implementation | analysis

`gate.py` reads it from `.review/next.md` (or the oldest `.review/queue/*.md`
when there is no `next.md`) and writes it into the gate log as field 12, so
every gate row says what kind of work produced it.

Why. The log records which model ran a session, how long the gate took and how
many tokens it cost, and that invites the obvious question — which model is
better value. It cannot be answered, because a diagnosis session and an
implementation session are not the same job: one reads and reasons, the other
edits and re-runs the gate until it is green. A per-model average over an
unknown mix of the two measures the mix at least as much as the model. On
2026-09-17 an attempt at exactly that comparison over 988 rows found every
difference confounded, and this is one of the two things that were missing.

Declared, not inferred. `gate.py` has the task file open in front of it and
could classify it from its prose. It deliberately does not. An inferred shape
always fires and is sometimes wrong, and a wrong shape is invisible — it puts
the row in the wrong bucket and moves an average with no trace. A declared
shape can be forgotten, and then the field is `-`, the row drops out of the
comparison, and the count of `-` says how much was lost. **Missing data
narrows a result; wrong data corrupts it while looking fine.** This log has
already paid for one confidently-wrong field and should not buy a second.

Writing the line is the task author's job, in the same block as `Written:`.
Nothing blocks when it is absent.

## A task declares its priority — added 2026-09-19

A task file may carry one line, in the same block as `Written:`:

    Priority: urgent | normal | background

Absent means `normal`. `~/bin/queue-runner` orders the tasks it is choosing
between by this first and by `Written:` second, so an urgent task written this
morning goes before an ordinary one written three days ago, and a background
task waits behind anything else that is eligible.

Declared, not inferred, for the reason SHAPE is: a priority guessed from the
prose would always fire and would sometimes be wrong, and a wrong priority is
invisible — it silently reorders the queue. A forgotten one is just `normal`.

### What priority is not

Priority is not the budget. The runner now spends the weekly allowance evenly
— roughly the remaining percentage divided by the days left before it resets,
capped at 15% a day — and reads how much has gone from `~/.claude/state/usage.tsv`,
which `~/.claude/statusline.sh` journals a row a minute from the numbers Claude
Code hands it. When today's spend is past that line the runner admits only
tasks that are `Priority: urgent` or `Weight: light`; when it is past the whole
day's budget, only `urgent`. In the last hours before the weekly reset it
spends whatever is left, because an allowance that does not roll over is worth
nothing unspent.

So the two do different jobs, and a task should set both honestly:
**priority decides what goes first, weight decides what still goes when the
budget is tight.** Marking everything urgent does not buy more allowance; it
only removes the runner's ability to tell which task mattered on the day there
was not enough to go round.

Missing or stale usage data admits rather than holds, like every other sensor
in that runner.

## Every repo declares what it is in service of — added 2026-09-06

Thomas, after reading about people who spent months with an agent on something
that could not be built: *"AI will never tell u if the project cannot be made
or ur idea is bad, and it'll just keep going until u cant go anymore."*

So every repo with a `.review/` directory carries `.review/BLOCKER.md`:

```
# <one line: what "done" looks like for this repo right now>
check: <shell command; exit 0 means the blocking step has CLOSED>
falsifier: <what would show this direction is unachievable>
```

`sunk-cost` reads it across every repo and fires when a repo ships 30+ tasks in
a week with its blocking step still open, when 60+ tasks ship across all repos,
or when a repo has **no** BLOCKER.md at all — which is the most exposed case,
not the safest, because it means tasks are shipping with nothing to be in
service of.

The `falsifier:` line is the part that matters and the part that is hard.
**A direction with no falsifier is the trap by definition.** It must describe
evidence that would make you stop, not a difficulty you would push through. If
you cannot write one, say so in the report — that is a finding about the
direction, not a formatting problem.

Before queueing work into a repo, run `sunk-cost`. **When it is lit, do not
queue another task.** Read the falsifier, ask what would have to be true for
the direction to be unachievable, and go and check that instead.

## Queue files carry a timestamp — added 2026-09-09

`/review` takes the **oldest by filename** from `.review/queue/`. That only
means "oldest" if the filename starts with one.

On 2026-09-09 the iris queue held eleven tasks written by two chats across five
days. One used `2026-09-04T2200-...`; the other used bare descriptive names. So
filename order was alphabetical, digits sorted before letters, and the queue ran
in an order nobody chose. Two chats then gave Thomas contradictory accounts of
the same repo — one saw one task waiting, the other found eleven.

**Name every queue file `YYYY-MM-DDTHHMM-<slug>.md`.** Nothing else enforces
order, and a queue without an order is a pile.

Two rules that follow:

* **Before adding to a queue, read what is already in it.** Several chats write
  to the same one. A week-old queue will contain duplicates and at least one
  task already done — running those in arbitrary order is how contradictory
  changes land.
* **Do not report queue state from a summary.** Both accounts above came from
  memory rather than from `ls`. Check the directory.

## Rules that do not change

* **Claude Code implements; the chat session reviews.** A system that both
  makes a change and judges whether the change passed is a failure mode this
  work has hit repeatedly. Do not merge the roles.
* Diagnose before fixing. One thing per commit. Never weaken a failing check
  to make it pass. Say where every number was measured.
* An exit status of 0 is not evidence. Read state back after every change.
  `pmset -a autorestart 1` returns 0 on hardware that does not support it, and
  that false success shipped once already.
* A mechanism that has been installed but has never fired is not evidence that
  it works.
* Thomas still decides. Anything needing a judgement call stops and asks
  rather than proceeding on an assumption.

## Files

* `next.md` — the current task. Overwritten each cycle.
* `report.md` — the last full report. Overwritten each cycle.
* `archive/` — completed tasks and their reports, kept.
* `running` — lockfile while a session is in flight.
* `done` — the title of the last completed task.

`next.md` and `report.md` are working files, not history. Git history is the
record.
